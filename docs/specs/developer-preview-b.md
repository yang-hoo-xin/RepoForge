## Problem Statement

RepoForge 已有真实任务交付、受控执行和可分发开发版本，但外部开发者仍需要一条不依赖维护者临时目录的使用流程。真实模型调用存在累计费用不可预期的问题；新建源码和测试、审阅后应用及撤销也必须在同一版本中贯通。

## Solution

交付 Windows x64 上的本机 CLI，服务已有 SDK-style C# 仓库、构建和测试入口且能够审阅代码的开发者。用户提交小范围修改需求，自带模型配置和云端 Key、明确任务最高费用；系统在独立副本内调查、修改、验证与修订，交付补丁、测试报告及适用产物。用户审阅后决定应用到原仓库，并能撤销本次修改。

为什么要有它：以真实使用流程定义有限版本，现有功能和证据可复用，不把整个研究队列变成试用前置。

本版区分三个结果：产品任务交付是完成该任务适用检查并提供对应源码版本的可审阅、可应用结果；正式评测中的正确交付要求同一最终版本通过该协议的独立验收并完成实际交付；用户采用是使用者实际接受并使用修改。各开发页按[文档管理约定](../document-management.md)核对当前正文、源码版本和实现归属。B4 的工程就绪不等于 B5 的用户采用，普通任务也不自动继承正式评测的隐藏验收准备。
为什么要有它：把已确认的语义接入实际规格，防止词汇表更新后工单仍按另一套含义执行。

## User Stories

1. 作为开发者，我希望从说明中的版本安装 CLI，以便不依赖维护者工作区。
2. 作为开发者，我希望启动前检查环境、项目和命令，以便错误配置不先消耗模型费用。
3. 作为开发者，我希望提供已有 C# 仓库和小范围期望行为，以便处理自己的真实需求。
4. 作为开发者，我希望自行选择支持的云端模型和 Key，以便掌握账户与费用。
5. 作为开发者，我希望可选择支持的本地模型，以便保留本地推理方式。
6. 作为开发者，我希望每个付费任务有明确上限，以便不会无限重试收费。
7. 作为开发者，我希望系统在下一次可能超额的调用发送前拒绝，以便上限是执行约束。
8. 作为开发者，我希望恢复继承累计费用与未知在途消耗，以便中断不重领预算。
9. 作为开发者，我希望模型只在获准目录中执行获准的修改或新建操作，以便保留源码控制权。
10. 作为开发者，我希望新源码和开发测试真正进入构建及检查，以便新文件不是未验证的附件。
11. 作为开发者，我希望模型利用公开失败反馈修订，以便完成实际业务修改。
12. 作为开发者，我希望看到失败、未执行和已交付的区别，以便正确判断结果。
13. 作为开发者，我希望审阅具体补丁、测试结果和费用后再决定是否应用。
14. 作为开发者，我希望应用前检查原仓库是否变化，以便避免覆盖其他工作。
15. 作为开发者，我希望撤销本次应用而不丢失其他修改。
16. 作为开发者，我希望任务可以停止、保存进度并说明续接条件，以便遇到错误仍可控制流程。
17. 作为试用者，我希望能够说明是否采用结果及原因，以便维护者改进实际阻断。
18. 作为维护者，我希望分别记录安装帮助、业务提示和手工代改，以便不将辅助成果说成独立完成。

## Implementation Decisions

- 复用正常 Task Run、现有 CLI、ArtifactStore、模型适配器、公开检查及交付机制；不新增平行任务执行器。为什么要有它：避免演示路径和实际产品路径分离。
- 普通试用使用需求、项目测试和用户审阅；允许补普通开发测试，冻结验收输入仍只读。为什么要有它：真实需求不应每次先制作隐藏评测题，模型也不能改写冻结裁判。
- 费用上限由用户明确给出，按当前任务绑定的模型、目的地、币种和费率校验；调用前保留保守的最大成本，再根据可信用量结算，未知消耗不得按零释放。不依赖缓存折扣来保证上限。为什么要有它：事后统计和平均价格不能阻止下一次请求超支。
- 费用恢复、重复回执和传输重试沿用同一账本；本版本不自动追加费用、换模型或改变外发范围。为什么要有它：中断和重试不能成为隐形续费路径。
- 目录编辑权限与向原仓库应用的批准分别核对；独立目录不声称是恶意代码安全沙箱。为什么要有它：许可生成候选不等于许可覆盖用户当前源码。
- 首批支持 UTF-8 C# 源码和获准开发测试的修改、新建，沿用已接受的 [ADR-0005](../adr/0005-task-permission-scope-and-file-creation.md)；删除、重命名及构建配置更改不自动开放。为什么要有它：复用已确认的权限设计，同时限定可完整验证的操作。
- 权限不足时保存并明确停止；完整动态扩权、挂起决定和关联新运行续接保留为后续工单。为什么要有它：已接受设计不必全部成为本轮试用前置。
- B1、B2 无前置依赖；B3 依赖 B2；B4 依赖 B1、B3；B5 依赖 B4。为什么要有它：每张工单交付一条完整行为，只声明真实阻断。

## Testing Decisions

沿用已确认的用户流程作为最高层验证入口：

- 正常 CLI / Task Run：受控提供方检验预算拒绝发生在 HTTP 前、停止与恢复不重置累计费用；验证请求、候选和错误终态。为什么要有它：不以内部账本单测冒充正常入口受控。
- 正常候选与交付入口：覆盖新建、修改、公开失败修订、恢复、审阅、精确源码应用和撤销，保留冲突反例。为什么要有它：操作必须贯穿实际使用方。
- 安装后的 CLI：在干净环境检查文档命令和一条完整流程，源代码、安装包及验证绑定同一提交。为什么要有它：源码目录可运行不等于安装包可用。
- 外部试点：至少两位非项目开发者各带一个真实需求，至少一项修改实际采用；保留拒绝、失败、耗时、费用和人工帮助。为什么要有它：分别验证可使用和对用户有用，不用人数冒充统计代表性。

## Out of Scope

公网托管、多租户、账号收费系统、任意语言/仓库、跨平台保证、从零生成大型项目、自动远端提交、部署服务或启动游戏、策略学习及完整竞争性评测。

为什么要有它：这些工作保留原队列，本轮工程就绪或试点得到明确阻断后再排序，不删除长期目标。
