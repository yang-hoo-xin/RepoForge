# RepoForge 持续工程目标增量：自主开发、实验与经验学习

更新：2026-10-22。状态：本线程讨论采纳的首选设计与实施要求；不是能力完成报告。此文件已登记到仓库工程目标，应用内目标模式的 objective 正文尚未同步：当前工具不支持编辑进行中的 objective。不得以本文件登记冒充应用内登记成功。

## 1. 目标、继承关系与优先级

持续建设面向本地和异构模型、以源码证据和真实测试约束交付的 Coding Agent 评测与执行平台。最终由用户通过正常入口取得满足需求的可用源码、产物和适用验证结果。当前优先解决真实模型面对业务错误时的自主调查、假设检验、技术方向调整、当前代码修订与完整交付；将可验证的跨任务经验改进作为本轮明确工程方向。为什么要有它：可靠交付需要完整的行动与反馈条件，长期学习也需要落实到后续真实任务的决策和结果。

本增量与原持续工程目标共同生效。原 Goal、R01–R18、14 个子验收、既有依赖与冻结成绩继续保留，冲突处按最新明确用户指令处理。v0.1 发布条件与长期产品完成条件分别判断；不恢复用户已取消的自主业务修复、真实服务重启、外部题模型交付三项 v0.1 前置限制，也不将发布成功视为长期目标完成。为什么要有它：恢复可靠性主线不能抹去历史要求，也不能把已撤销的发布门槛重新加入。

模型调用、读取、搜索、反馈字节、隔离编译和累计资源继续计量，旧 8 GiB 或 30 分钟窗口不作为一般运行前置门槛。真实授权、实际容量、平台硬限制及未知副作用仍按有效执行合同处理。为什么要有它：工程连续推进应复用现有授权，同时保留真实资源事实和执行边界。

## 2. 首选架构与正常任务

首选架构为：任务保存需求、当前代码、实际观察与累计资源；一个连续 Task Agent 负责技术假设、调查、实验和修改计划；平台独立管理权限、源码身份、执行副作用、工件与验收。LangGraph、ArtifactStore、Trace、现有构建和权限后端按适用性复用，允许跨模块修正不合理的接口与状态归属。为什么要有它：技术计划需要随证据变化，执行真实性和用户授权需要稳定的独立责任方。

以“配置更新后，已有查询对象读取新值，同时保留正常缓存行为”为例，期望模型自行阅读更新入口、对象生命周期和缓存；提出更新未生效或旧对象保留状态等假设；设计更新前后创建对象的对照；根据观察选择新的修改位置；修改候选并复验新值与缓存保留行为；最终由平台核验同一版本的源码、测试和交付产物。此例是设计验收场景，不是已有成果。为什么要有它：正常任务能检验各项能力是否协同，而组件存在不能替代完整用户过程。

任务开始只建立足以安全工作的合同：原始需求及来源、明确保留义务、已授权读写与执行范围、验收输入和确实影响工作的歧义。可确定的内部字段由程序处理；技术规划允许在调查中形成和修订。真正影响需求含义的未知须澄清或明确保留，模型派生建议不得升级为用户要求。为什么要有它：前置格式不能消耗主要解题成本，简化前置流程也不能造成需求遗漏。

## 3. 授权与技术计划分离

模型可以自主选择授权范围内的新目标、跨文件修改、实验顺序和实现方向。当前 Plan 选中的目标不等于用户授权全集；普通授权内目标调整优先由平台确定性建立版本绑定，不强制经过 Evidence 与 Planning 两轮模型审议。Evidence／Planning 保留为复杂影响分析、依赖不确定和证据冲突的可用能力。为什么要有它：正常开发经常改变修改位置，协调成本应对应实际问题而不是固定阶段。

建立新绑定必须核验实际授权、规范化路径、源码版本、当前读取证据、精确前像、禁止修改对象和已知副作用；新增绑定不得授权修改冻结验收输入。跨文件修改需要覆盖受影响调用者与保留行为。计划变化后分别判定代码可继续操作、检查是否失效和审批能否沿用，保留已有候选与累计成本。为什么要有它：路径合法只说明允许操作，版本正确和修改合理仍需独立验证。

正式 Apply、部署与外部写入消费对应有效授权，真实来源必须记录；不得让模型文本或经验条目授予权限。为什么要有它：自主技术选择不能扩大实际执行委托。

## 4. 自主实验与独立验收

Task Agent 应能自主选择已有测试子集、在授权实验区创建和修订临时探针，并针对明确候选执行，取得真实观察、断言、退出状态与原始日志引用。实验内容、选择与修订由模型决定；平台约束版本、可执行能力和副作用。具体接口从当前任务与现有执行后端确定，不以两个新工具名或固定流程代替能力验收。为什么要有它：模型需要主动获取能区分技术假设的信息，仅调用固定 checker 无法覆盖所有调查问题。

探索性实验、公开验收和独立最终评测分别管理。模型可改探索实验；当次公开验收标准须冻结并保护；隐藏材料不进入求解反馈，且不能引入题面没有表达的业务要求。模型实验通过仍需正式验收支持交付。为什么要有它：探索允许试错，验收需要保持独立性和需求一致性。

实验执行边界以实际文件、网络和进程隔离为准。独立目录不等于安全沙箱；优先复用已获准的构建和测试能力，新增执行能力须对应真实权限与隔离实现。为什么要有它：临时探针执行的风险来自代码能力，不能用目录名称代替约束。

当前 Polly 的公开题面复现是建立有效反馈的起点；随后应验证模型能自行提出实验、依据反例改变方向，并在另一已有任务或运行格式中验证共享接口复用。开发者提供的公开测试只计为开发者辅助的反馈条件。为什么要有它：手工补充反例与模型自主设计实验是不同能力，演示脚本不能长期承担产品缺失逻辑。

## 5. 长期经验的对象与生命周期

模型权重先保持固定，分开管理当前任务状态、不可变执行经历、策略经验和带版本的仓库知识。任务状态保存当前候选、确认事实、被反驳假设与未知观察；执行经历复用 Trace 与 ArtifactStore；策略经验描述适用条件、候选解释、建议实验或调查、反证条件、来源、适用范围与状态。为什么要有它：持续施工、事实追溯与跨任务改进有不同用途，记录成功补丁并不自动形成可迁移策略。

在有信息增量时自动提炼候选策略，例如假设被实验推翻、候选出现有效修订或任务终止；由程序核验来源、候选身份和数据使用范围。候选策略经限定范围试用，根据后续结果保留、修订、收窄或停用；人工处理有歧义、冲突或高影响内容，不设置逐条人工审批为默认流程。为什么要有它：经验需要可更新和可撤回，来源真实也不能证明策略有效。

经验按任务、运行时、版本与适用条件筛选，在任务开始、新反例、假设被推翻、重复无信息行动或模型主动请求时按需检索，直接进入 Task Agent 技术决策输入。记录经验版本、来源、输入身份、注入时机与实际送达；让当前源码和实验能够推翻历史策略。为什么要有它：经验必须能影响行动，同时控制上下文噪声和错误套用。

工具基本用法、版本语义、错误纠正提示须共同提供给 B 和 B+。补齐工具说明或重复提醒的收益单独归因，不据此宣称长期学习；开发者撰写的策略标识其人工来源，系统自动提炼并迁移到新任务须另有证据。为什么要有它：工具可用性、提醒效果和自动经验改进不能混为同一种成绩。

不预设固定条数、使用次数或模型自评置信度作为成熟门槛。经验版本允许保持试用、限定场景启用或默认关闭；已有 Self-RAG、LoRA/SFT/DPO 等研究义务保留其依赖与验收，不成为本轮策略学习的前置条件。为什么要有它：采用范围应由真实收益与负迁移决定，机制数量和训练动作不能代替结果。

## 6. 评测驱动开发与归因

主要分析单位是“技术判断—行动—实际观察—后续决定—任务结果”。检查调查是否提供判别信息、实验是否真正执行、反例是否促成有效修订、保留行为是否退化、最终交付是否与被测版本一致。模型未表达的假设记为未明确表达；行为分析须标注为分析，不补写当时推理。为什么要有它：工具次数和事后解释不能证明决策改善。

基础 B 与 B+ 在行动、反馈和执行条件有效且可比较时即可开展经验比较，不要求 B 先修对所有题目，也不要求所有产品功能先完成。两组共享模型、工具说明、反馈、授权与资源策略；B+ 仅增加本批明确研究的策略经验。若比较整体架构可整体改变相关机制，只有声称单项因果贡献时才要求隔离该因素。为什么要有它：既避免把学习研究无限推迟，也避免在不公平条件下解释收益。

经验版本在比较批次前冻结；隐藏评分不用于批次中途调优。先比较相关机制在不同实现或仓库中的近迁移，并加入不适用场景检查负迁移，再决定是否扩大缺陷家族。比较新旧经验版本时使用同一批新任务，曝光题转为开发回归；样本规模随问题、成本与不确定性决定。为什么要有它：题目难度、曝光和实验条件变化都可能伪装成经验进步，小型批次也不能支持普遍可靠结论。

同时报告全部启动任务的正确交付、有效评测比例、有效条件下的任务成功、有效修订、保持义务、全部时间和已知成本、未知用量、人工帮助与负迁移。经验提炼、检索、失败尝试和平台中断计入成本；前置失败保留在端到端分母。为什么要有它：分离原因有助于修复，不能通过排除产品失败美化用户实际结果。

## 7. 评估器与记录本身的验收

用已知动作验证记录的漏记、重复、顺序、请求响应关联与成本统计；用中断恢复、旧报告、错版本候选检查结果绑定。执行事实与评估结论分开，保留原件与评估器版本。为什么要有它：错误轨迹会制造错误归因，判断也不能覆盖历史事实。

按风险用原实现、正确实现、合理等价实现和错误变体验证验收器的误拒与漏检，确认测试实际执行，覆盖零测试成功退出、框架崩溃、旧报告复用及错误候选交付。语义评估允许无法判断，不把评估器自身或另一模型的同意当作真值；更新后复验受影响结论。为什么要有它：扩大自主能力需要可靠判定，形式通过不能证明业务结果。

通用观测继续复用 Langfuse，本地记录聚焦候选、检查、恢复与交付关联；只补影响归因、复验和验收的缺口。为什么要有它：记录服务于工程处置，不能另起与自主修复竞争的观测工程。

## 8. 接入范围、当前切入点与完成标准

前置任务合同、授权内新目标绑定、自主实验、经验注入和生命周期必须通过正常入口及共享模块接入，处理版本变化、中断恢复、旧调用者、累计资源和最终交付；外层主 Agent 对集成和最终使用过程负责。为什么要有它：一条实验脚本通过不能证明用户能够使用产品，也不能把多个局部完成相加成整体完成。

当前承接 Polly 最新真实运行与保存候选，B5–B11 保留历史身份与失败；B12 已启动，结束前不重复启动。先核对其是否越过上下文阻断、是否收到业务反例与形成有效修订，再选择直接修复或后续实验。平台／验收问题优先用保存候选走同一产品入口定位，再运行真实模型；每次重跑注明实际变化和要回答的问题。为什么要有它：新设计应推进现有任务，模型运行不应反复承担执行器接线调试。

采用条件不是一条串行闸门：当前运行收尾与有效业务反馈是近期切入点；自主实验和目标调整围绕完整任务集成；经验实验在具备可比行动与反馈时开展，可与交付完善共同推进。服务可靠性、实机、发布和其他专项仍按原依赖选择；插队说明延后项、原因与返回点。为什么要有它：不能用“先把基础全部做好”无限延后学习，也不能用新辅助模块长期悬置当前任务。

阶段完成分别需要：真实模型自主选择有判别力的动作；反例促成可核验的判断或实现修订；授权内跨目标修改能够执行并恢复；正式验收及交付绑定同一源码；经验进入真实决策并在新任务上评价收益与负迁移。未满足者保留未完成，负结果可结束某项方案试验但不关闭原产品缺口。为什么要有它：平台通路、单题自主修复、跨任务经验收益和整个 Goal 完成具有不同证据要求。

## 9. 采用、收窄与撤回决策

若自主实验帮助模型推翻错误假设、形成有效修订并改善交付或同等正确性下的成本，继续该方向；若探索与无关修改持续增加，检查直接原因并缩小采用场景或比较更合适模型。若确定性绑定减少协调并支持正确跨文件修复则采用；若需求遗漏与退化增加，修正影响检查或收窄对象。为什么要有它：首选设计需要充分实现和公平验证，也必须允许证据推翻。

若策略在新任务改善结果或效率且负迁移可控，保留并扩大验证；若仅等同工具提醒，改归因；若错误套用或成本抵消收益，修订、收窄或停用。若新经验版本在同批新任务无改善，不宣称积累使系统越来越聪明。为什么要有它：经验数量、检索命中与模型自述均不能替代持续收益。

整个 Goal 仅在所有适用既定条件都有当前证据时完成；本文件同步、一次成功、实验不采用或发布收口都不能替代该审计。为什么要有它：目标应持续约束实际交付，而不是随已经完成的工作缩小。
