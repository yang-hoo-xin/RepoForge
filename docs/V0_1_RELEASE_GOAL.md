# RepoForge v0.1.0 迭代发布目标

状态：当前最高优先级，建立于 2026-10-21。它决定 v0.1.0 发布前的工作选择和停止条件；历史需求、实验原件与长期 Backlog 继续保留，但不再自动成为本版本的发布门槛。

为什么要有它：过去的真实交付、统一评测、服务可靠性和研究专项不断累积，却没有一个有限的版本完成点，导致局部问题和长期义务反复挤占可发布成果。

## 1. 版本目标

RepoForge v0.1.0 定位为：

> 面向本地和异构模型、以源码证据和真实测试约束交付的 Coding Agent 评测与执行平台。

本版本交付一份可从干净源码快照复现、能够通过正常入口运行、结果边界明确的初始开发版本。它证明平台能够组织源码调查、候选修改、真实验证、结果追踪和受控交付；不承诺任意任务都能由模型自主修复，也不宣称生产级服务成熟度。

为什么要有它：v0.1.0 需要有可兑现的公共承诺；“初始开发版本”允许后续接口变化，但不能用长期愿景代替当前可运行结果。

## 2. 本版本必须交付的内容

1. **准确的公共定位。** README、仓库描述和文档入口使用上述平台定位；C#、Unity、BepInEx、IL2CPP、Harmony 和 GTFO 保留为已验证案例或领域适配，不再作为整个产品的唯一身份。
   为什么要有它：公共描述需要覆盖普通代码库和多模型方向，同时保留具体、可核对的工程证据与检索关键词。

2. **可复现的正常入口。** 从干净 clone 和冻结依赖开始，用户能够执行文档中的无模型快速检查，并运行至少一条确定性的端到端演示，得到绑定源码、候选、测试结果和终态的产物。
   为什么要有它：发布版本必须让外部用户复现一条完整使用路径，不能依赖维护者机器上的临时目录、历史会话或口头说明。

3. **明确的结果分层。** 对外材料分别标注自主模型结果、开发者辅助结果、脚本或夹具验证、环境资格和未完成结果；失败、超时、未知用量及人工介入不被删除或合并成成功。
   为什么要有它：RepoForge 的核心价值之一是拒绝伪成功，发布材料本身也必须遵守同一证据标准。

4. **发布快照质量。** 当前改动整理为可审查提交，移除或忽略临时输出，精确发布提交通过选定的 v0.1 CI 与冒烟检查；从新目录复验文档命令和演示入口。
   为什么要有它：本地脏工作区和旧提交上的绿色 CI 不能证明即将发布的源码可安装、可运行或可恢复。

5. **发布基本资料。** 提供用户选定的开源许可证、版本说明、已知限制、安装和卸载/清理说明，以及 v0.1.0 标签对应的不可变内容。
   为什么要有它：公开源码不等于可复用版本，用户需要知道许可、版本边界、风险和如何取得同一份结果。

## 3. v0.1.0 发布验收

只有以下条件全部满足，才允许创建 v0.1.0 标签或 GitHub Release：

- 发布提交已确定，工作树中属于本版本的源码、测试和文档均已纳入提交；无凭据、机器私有路径或必要文件遗漏。
- `uv lock --check`、冻结依赖安装、致命 Ruff 检查、当前受支持的 CI 检查集和 v0.1 冒烟测试在该提交通过。
- 干净 clone 能执行 README 的快速开始；确定性演示从正常入口完成并生成可检查结果。
- README、实测结果和 Release Notes 对同一版本使用一致的能力边界、数字和证据来源。
- LICENSE、版本号、已知限制和回退到发布提交的方法齐全。
- GitHub 上的 CI 对精确发布提交成功，之后才创建标签和 Release。

为什么要有它：发布判断需要绑定同一个不可变提交和外部可重复流程，不能把不同日期、不同工作区和不同检查结果拼成版本通过。

## 4. 当前不阻塞 v0.1.0 的工作

以下事项继续保留，但不是本版本前置条件：

- C5 业务错误的新增自主修复成绩及第二客户端实机；
- Serilog 外部题的 A / A* / B 模型对照和模型交付；
- Docker / Redis 的真实重启、重放、回退和长期运行验收；
- 任意 C# 仓库的自动配置、操作系统级沙箱和生产级远程执行；
- 百并发、大语料、有模型服务压测；
- Self-RAG、LoRA、SFT、DPO、自动跨任务经验学习和完整十题收口；
- 稳定公共 API、向后兼容承诺和 v1.0 生产成熟度。

这些事项只有在修复直接阻断 v0.1 正常入口、发布快照或证据准确性的问题时，才允许在发布前插队。

为什么要有它：这些工作有长期价值，但把它们全部设为首版门槛会再次造成无边界扩展；明确例外也避免发布目标掩盖真实阻断。

## 5. 迭代里程碑

### M0：目标与发布清单冻结

- 建立本文件并让当前计划、项目状态和文档入口指向它。
- 盘点当前修改，将 v0.1 必需项、历史证据、临时输出和后续 Backlog 分开。
- 确定公共定位、演示入口、许可证待选项和发布检查命令。

完成点：仓库中存在一份有限、可核对的 v0.1 清单，后续工作能逐项关闭。

为什么要有它：先固定发布判断，才能避免开发过程中再次把新建议自动扩成新的前置链。

当前检查点：公共定位、有限门槛、非阻塞项、许可证、Changelog、候选Release Notes和正常入口演示命令已建立；演示在开发态真实`.NET 8`环境通过两种技术路径。尚未完成当前WIP整合、精确候选提交、干净clone、候选提交CI和修订绑定发布证据，因此M0/M1仍在进行。为什么要有它：阶段状态必须同时记录已完成项与直接缺口，不能因演示通过跳过发布快照收口。

### M1：源码与文档收口

- 更新 README、文档索引、当前状态和公开结果的版本口径。
- 将当前公共实现拆成职责清楚的提交，保护无关 WIP 和历史原件。
- 清理发布范围内的机器私有路径、临时目录引用和过期入口说明。

完成点：候选发布 diff 可审查，公共文档只承诺当前版本能够复现的行为。

为什么要有它：发布首先是一个可理解的源码快照，不能让历史研究记录替代产品边界。

### M2：可复现入口与发布门禁

- 从干净目录安装冻结依赖并运行快速开始。
- 通过正常 CLI 执行确定性端到端演示，核对源码、候选、测试、产物和终态关系。
- 把必要冒烟检查接入 CI；保留现有内部 Alpha 检查的真实名称和覆盖范围。

完成点：相同提交在本地干净环境与 GitHub CI 都能得到一致的发布判断。

为什么要有它：本机已有缓存和临时文件可能掩盖缺失依赖、错误路径和未提交文件。

### M3：版本发布

- 加入许可证、`CHANGELOG` / Release Notes 和已知限制。
- 核对发布提交、CI、文档链接、示例输出和无敏感信息结果。
- 经用户确认后创建 v0.1.0 标签和 GitHub Release；发布后不修改同一标签内容。

完成点：GitHub 上存在可下载、可复现、说明准确的 v0.1.0。

为什么要有它：外部发布会形成长期引用，必须在不可变版本和最终说明一致后执行。

## 6. 执行与插队规则

当前连续执行顺序为 M0 → M1 → M2 → M3。发现缺陷时，若它直接阻断当前里程碑，就修复并复验；若属于非阻塞长期能力，则记录到原队列并继续当前里程碑。

新问题可以插队，但必须记录被延后的 v0.1 工作、插队原因和返回点。咨询、评估或新的实验建议本身不自动改变发布优先级。

为什么要有它：发布目标需要允许必要修复，同时防止新的辅助模块、实验或报告再次无限延后版本收口。

## 7. 历史任务的恢复点

v0.1.0 发布完成后，重新从现有证据选择下一项，而不是自动恢复全部旧队列。首轮候选为：自主业务修复的模型能力上限对照、Serilog 独立任务、服务真实重启，或用户另行指定的 v0.2 目标。

为什么要有它：历史工作没有被删除，但发布后仍应按收益、依赖和当前条件重新选择，不能让旧顺序重新变成永久门禁。
