# 项目文档的存放、关联与清理

适用范围：RepoForge 的 PRD、Spec、实施计划、ADR、研究分析、HTML 报告及其 GitHub Issue／PR 关系。已接受的选择是：仓库保存正文，GitHub 管任务与 PR，统一索引连接两者。

## 从哪里开始

总入口是 [docs/README.md](README.md)。[文档总览](index.html)由 [登记表](document-registry.json)和仓库正文生成；GitHub 状态显示的是注明时间的读取快照，打开 GitHub 链接可以核对最新状态。

```text
python -m scripts.project_docs build
python -m scripts.project_docs check
python -m scripts.project_docs search B4
```

为什么要有它：人和 Agent 使用同一入口，生成视图可以重建，正文和任务状态保留各自来源。

## 正文与状态归属

| 内容 | 存放位置 | 负责的事实 |
| --- | --- | --- |
| 产品目标／PRD | 指定产品合同与父 Issue 的目标摘要 | 面向谁、解决什么、验收范围 |
| 功能规格 | `docs/specs/`；正式采用的 OpenSpec 规格需显式登记 | 应有行为与验收场景 |
| 架构决策 | `docs/adr/`，沿用既有编号 | 决定、取舍及替代关系 |
| 调查与分析 | `docs/research/` | 结论、适用版本、证据和未知项 |
| HTML 报告 | `docs/reports/` | 可阅读报告；来源清单记录原件身份及必要处理 |
| 未确认正文与待发任务 | `docs/drafts/`，稳定 ID 对应固定路径 | 草稿、待确认、待 GitHub 发布；不能冒充正式正文或远端工单 |
| 任务、依赖和负责人 | GitHub Issues | 执行状态、下一步、对应规格 |
| 拟合入的代码／文档 | GitHub PR | 差异、测试、审阅和合入结果 |
| 原始实验记录 | 既有 `artifacts/`、ArtifactStore、Trace | 当次实际发生的结果，索引只引用 |

每份正式正文在登记表中有稳定 ID、类型、状态、路径、所属工作线和来源。关联使用这些 ID 或真实 GitHub URL；B4、S2 等局部编号应同时显示所属工作线。为什么要有它：同名文件或局部编号不能确定版本和任务身份。

同一事项指定一份当前正文；其他分支副本按来源提交登记为版本快照。设计接受、工程实现、验证、合入、发布各自记录，不能由文件存在推导成功。为什么要有它：文档迁入主线不意味着相应功能代码已经合入。

## 日常维护

### 草稿如何成为正式正文

每个事项先选一个稳定 ID。新建 Markdown 草稿进入 `docs/drafts/<ID>.md`；后续修改更新同一条登记和同一文件，不另建日期版、v2、final 等平行正文。Git 提交保留修订历史。为什么要有它：草稿需要有归属和连续修订，文件名不能变成第二套版本系统。

正文确认后使用 `promote`：提供确认依据、当前原文字节哈希和正式目标路径。工具检查源草稿未被他人改动、目标不存在，再迁入规格／ADR／研究目录，保留同一 ID、确认依据和前后内容身份。旧位置只保留跳转页，并从正文发现列表排除。为什么要有它：确认必须落到一份准确正文，转正不能产生两个都可继续编辑的副本。

不再采用的草稿用 `retire` 登记原因与决定依据，退出默认列表。仍有未完成内容或引用的草稿先核对，不通过年龄自动转正或删除。为什么要有它：每个草稿要有实际去向，同时保留必要的恢复和追溯能力。

```text
python -m scripts.project_docs draft --id <ID> --title <标题> --kind spec --content-file <仓库内输入.md>
python -m scripts.project_docs promote <ID> --to docs/specs/<名称>.md --decision-ref <用户确认或Issue决定> --expected-sha256 <当前草稿原文SHA256>
python -m scripts.project_docs retire <ID> --reason <原因> --decision-ref <决定依据> --expected-sha256 <当前草稿原文SHA256>
```

GitHub 待发任务使用 `pending-publication`，不走正文 `promote` 来伪造发布。只有取得真实 Issue／PR URL 并核对提交内容后，才将同一 ID 的正文定位改为远端 URL；本地草稿可变成短跳转页或在修复入链后删除。发布失败继续保留待发状态和具体错误。为什么要有它：正式正文确认与外部任务发布是两种结果，连接器失败不能留下无人管理的“已完成草稿”。

新增或修改正式文档、任务状态或报告时，更新对应正文和登记关系，再运行 build/check；普通代码修改只在确实影响文档时维护。使用 [project-docs-maintainer](../.agents/skills/project-docs-maintainer/SKILL.md) 完成批量整理。为什么要有它：持续维护是交付的一部分，不能每次都重新盘点全磁盘。

GitHub 原对象通过连接器或已授权客户端读取；更新登记表中的状态与时间，不复制整份 Issue／PR 正文建立另一套可写队列。远端发布失败时明确保留为本地草稿，不虚构编号。为什么要有它：索引可以离线查阅，但不能冒充实时任务系统。

索引自动发现未登记的旧文档时标记为“未分类”，供后续判断；不得按日期或文件名推断它是现行规格、已完成工作或可删除垃圾。为什么要有它：发现文件和确定权威归属是不同步骤。

## 迁移和清理

同内容的 Git 工作树副本保留在 Git 管理下；总览可以按身份合并展示。将长期正文从临时目录收回仓库时，记录来源、原文哈希、来源提交及必要的脱敏／链接处理。为什么要有它：整理需要可追溯，不能覆盖活动工作或让旧证据失去身份。

删除只用于已核对的重复导出、无独有内容的已替代草稿或可重建临时材料；先查代码、文档、任务和运行清单的入链，更新消费者，再在独立提交中删除并留下替代关系。活动计划、冻结验收和原始失败／成本／交付证据继续保留。为什么要有它：清掉无价值内容的同时，要保证当前工作和历史结论仍可复查。

HTML 盘点和搜索只提取文本，不执行报告脚本；本机路径、密钥及私有验收内容不进入公开索引。原 HTML 的处理方式在来源清单说明。为什么要有它：一份报告是资料，不应在整理时获得执行权限或扩大公开范围。

## 现有材料的阶段

本轮索引以远端 main `0e688f9cdfd25f155bcb74d14da535d4482978c8` 为整合基线，补充已确认的开发者试用版、候选接口、验收接线、B1 审查及 HTML 报告来源。其他工作树的代码保留原分支；历史状态文档继续可查，默认入口指向明确工作线和 GitHub 任务。

OpenSpec 当前仍是独立试用，不覆盖原权威规格。正式采用时再迁移对应正文、更新消费者和替代关系。为什么要有它：避免在旧规格之外增加一份平行维护的现行要求。
